# Contributing

Thanks for considering a contribution to Agent Forecast, which is live on the
[Shopify App Store](https://apps.shopify.com/ai-forecast-agent). Because real merchants use it,
PRs are reviewed and merged by the maintainer only, and changes are tested against a real
development store before they ship. That can take a few days.

## Project rules

- **Math stays pure and tested.** `app/lib/forecasting.js`, `preorder.js`, `reorder.js` and
  `order-usage.js` are deterministic: no side effects, no network, no AI calls. Changes to them
  need fixture tests in `test/`.
- **The AI only explains numbers.** The agent (`app/lib/ai-agent.js`) works from a snapshot the
  server builds from the database and the Shopify Admin API. It never produces or invents a
  figure.
- **Never commit secrets.** No `.env`, API keys, `ENCRYPTION_KEY`, tokens or database files.
  Use `.env.example` for variable names only, and check `git status` before pushing.
- **Read-only scopes only.** The app requests `read_inventory`, `read_locations`, `read_orders`
  and `read_products`. Any new scope needs the maintainer's sign-off in an issue first, and a
  fresh App Store review pass, so please don't include one in a PR out of the blue.
- **No new dependencies** without discussing it in an issue first.

## Setup

See the README's "Local Development Quickstart". You'll need your own free Shopify Partner
account and development store (this repo can't provide one) and a local PostgreSQL database
(for example Postgres.app); the app doesn't run on SQLite. **Never point a local `DATABASE_URL`
at a production database.** If your change touches `prisma/schema.prisma`, include the migration
generated by `npx prisma migrate dev` against your local database.

## Before you open a PR

```bash
npm test            # Node's built-in test runner; no database needed
npm run build       # production build; CI runs both of these on every PR
```

- `npm run lint` is not set up yet (ESLint isn't installed), so it isn't a required check.
- Add or update tests for any change to the pure math or the webhook logic.
- Update the docs (README, `docs/WEBHOOKS.md`) when behavior changes.
- Describe what you tested and how in the PR description. A development-store screen recording
  or screenshots are appreciated for anything UI-facing.

## Testing webhooks safely

The order-webhook path is the most delicate part of the app. Read
[`docs/WEBHOOKS.md`](docs/WEBHOOKS.md) first. To exercise it end to end, use
`scripts/replay-order-webhooks.mjs` against a **throwaway localhost Postgres database** with
dummy secrets. It refuses to run against anything else, and it must never be pointed at
production data.

## What makes a good first PR

- Direct tests for `app/lib/forecasting.js` (the roadmap item in the README).
- Extra fixture cases for the existing pure math: edge cases, boundary values, bad input.
- Documentation fixes and clearer comments.
- Small, focused bug fixes with a test that fails before the fix.

For anything bigger than a small fix, open an issue first so we can agree on the approach.

## Security

Found a vulnerability? Please don't open a public issue. See [`SECURITY.md`](SECURITY.md).
